# Three.js 画面方案适配性评估

| 项目 | 内容 |
| --- | --- |
| 调研日期 | 2026-11-10 |
| 版本 | v1.0 |
| 调研对象 | [mrdoob/three.js](https://github.com/mrdoob/three.js)（r187 / npm `three@0.187.0`） |
| 需求来源 | 飞书：评估 Three.js 是否适合本项目的「战棋和场景画面」 |
| 一句话结论 | 库本身成熟、活跃、许可干净；但它是 **3D 渲染库**，不是画面方案本身。**当前不建议作为主画面方案**；只有确定走 3D 战棋 / 立体场景，并愿意配套 3D 美术管线时，才值得做单场景验证。 |

> 本文只评估 Three.js 与本项目画面方向的适配性，不改变现有设计文档和已上线原型。相关背景见 [画面 / UI 现成方案调研](game-visual-solutions-survey.md)。

## 0. 结论先行

1. **Three.js 从「能不能用」角度没有顾虑。** 118k★、MIT、2,600+ 贡献者、每周 3,500 万次 npm 下载、约 1–3 个月一版；WebGL2 主路径成熟，WebGPU 渲染器也已单独提供。
2. **它不适合替换现在的 DOM / SVG 主界面。** 本项目大部分画面是文字、词卡、按钮、表单和复习流程；这些用 DOM 排版、读屏、键盘操作、端到端测试都更直接。把文字搬进 WebGL 是负收益。
3. **对战棋和场景，它「有条件适合」。** 如果确定要可旋转、有高低差、立体棋子、真实光照的 3D 棋盘，Three.js 是 Web 端最合适的选择之一；代价是 3D 模型、贴图、绑定、动画、光照一整套美术管线，以及构建链和移动端性能验证。
4. **换渲染器不会自动让画面「像游戏」。** 现在缺的是角色 / 卡面 / 场景美术和动效，不是画不出来。Three.js 只负责把模型画出来；没有模型，它只能画出灰色方块，观感大概率不如现有的程序化 SVG。
5. **建议路线：当前不引入；若要做 3D，先在现有战棋原型上做「一场战斗」的 vertical slice，用中低端手机实测后再决定。** 不要整章、整游戏迁移。

## 1. 本项目画面现状与硬约束

| 层 | 现在用什么 | 规模 / 特点 |
| --- | --- | --- |
| 剧情与主界面 `game/` | 原生 DOM + CSS + 程序化 SVG（12 个镜头共用一个 1600×900 的世界） | 零运行时依赖；暗色文学感；键盘焦点、跳过链接、减少动效、移动端布局 |
| 5e 剧本原型 `prototype/sunless-keep/` | 原生 DOM + CSS；战棋是 DOM 网格 | 无构建、无外部资源；DM 对话 + 战术板 |
| 鸟瞰桌游战棋（PR #11，合并后路径 `prototype/tactical/`） | **Canvas 2D** 程序化绘制木桌、棋盘、棋子、道具 | 缩放 / 平移；全部由代码画，无图片字体依赖 |
| 工程 | 静态站点，GitHub Pages | 25 个单元 / 内容测试 + 10 个 Playwright 端到端用例；离线可玩 |

设计文档 8.1 对客户端的定义是「移动优先的 PWA；**文字 + 图标 + 少量插画**」。这是判断适配性的基线：本项目的主体是文字学习循环，不是 3D 世界。

硬约束：

- **静态托管**：GitHub Pages，纯前端，无服务端渲染。
- **移动优先**：手机竖屏是主场景，低端 Android 也要能玩。
- **可访问性**：键盘、焦点、读屏、`prefers-reduced-motion` 是已有能力，不能倒退。
- **可测试**：现有测试以 DOM 断言和页面错误收集为主；3D canvas 只能做截图 / 像素对比。
- **零运行时依赖**：不是宗教，但它是当前首屏小、离线稳、升级少的主要原因。

## 3. 适配度矩阵

| 画面需求 | 现在怎么做 | Three.js 能提供 | 判断 |
| --- | --- | --- | --- |
| 主界面、文字、表单、词卡、复习 | DOM + CSS | 需要把文字贴到 canvas / 用 HTML overlay；排版、选中、读屏都要自己补 | **不适合**：DOM 明显更合适 |
| 剧情场景（雾港、灯塔、海面） | 程序化 SVG，多镜头切换 | 3D 场景、真实光照、雾、粒子、自由镜头 | **有条件**：观感上限更高，但要有 3D 场景与道具 |
| 战棋棋盘（鸟瞰、棋子、地形） | Canvas 2D 手绘风，已支持缩放 / 平移 | 立体棋子、高低差、阴影、可旋转镜头、点击拾取 | **有条件**：3D 玩法成立时才值得 |
| 卡牌打出 / 受击 / 伤害数字 | CSS / DOM / Canvas | 3D 粒子、拖尾、屏幕特效 | **可用，但没必要**：2D 的 PixiJS / CSS 更轻 |
| 镜头转场 / 视差 | SVG viewBox + CSS | 相机路径、景深、动态光照 | **有条件**：是 3D 少数明显加分项 |
| 移动端 | DOM + 少量 SVG 动画 | GPU 渲染；阴影、抗锯齿、DPR 会吃性能与电量 | **需实测**：不能假设中低端手机稳 60fps |
| 无障碍 | 原生语义、键盘、读屏 | canvas 内容对读屏不友好，要另做 DOM 对照层 | **劣势**：需要额外成本补回 |
| 测试 | DOM 断言 + pageerror | 主要靠 canvas 截图对比，交互要模拟坐标 | **更难**：棋盘相关 E2E 要重写，文字 / 流程用例可保留 |
| 静态部署 | 零依赖、无构建 | 仍是静态站点，但建议 bundler 做 tree-shaking；也可 importmap 免构建 | **可行**：多一条构建 / 版本锁定链 |

### 3.1 关键认知：Three.js 不是游戏引擎

它是**渲染库**，不是 Phaser / Godot 那种框架。以下都得自己做或另找：

- 战棋规则、回合、网格、寻路、命中 / 视线判定（现有代码已有，不受影响）；
- 物理 / 碰撞、音频、UI、存档、资源加载管线、关卡编辑器；
- 3D 资源规范、模型导入、动画状态机、光照烘焙 / 调优。

所以换 Three.js **不会减少现有玩法代码**，只会把「2D 画棋盘」换成「3D 画棋盘」，并新增一批 3D 专属工作。

## 4. 成本实测（包体）

以下为 2026-11-10 本地实测：npm `three@0.187.0`，esbuild 0.25.0 `--bundle --minify --format=esm`，`gzip -9`。

| 方案 | 未压缩 | gzip | 说明 |
| --- | ---: | ---: | --- |
| 当前 `game/` 全部 JS + CSS + HTML | 186 KB | **42 KB** | 零运行时依赖的基线 |
| Three.js 全量 build（`three.module.js` + `three.core.js`） | 2.13 MB | **419 KB** | 用 importmap、不做 tree-shaking 时浏览器要下的量 |
| Three.js 最小 WebGL 场景（tree-shaken） | 537 KB | **133 KB** | 一个立方体 + 相机 + 光，不含任何业务 |
| 最小场景 + OrbitControls | 560 KB | **138 KB** | 加一个轨道控制器 |
| 战棋级依赖（glTF 加载 + 动画 + 阴影 + 雾 + 轨道控制） | 657 KB | **164 KB** | 仍**不含**模型、贴图、音频 |
| PixiJS 8 最小 Application（全量入口，2D 对照） | 528 KB | **153 KB** | 全量入口；tree-shaking 后会更小，说明 2D 渲染器也不是零成本 |

结论：

- **包体不是 Three.js 的致命伤**，164 KB gzip 对现代 Web 应用可以接受；但它把当前 42 KB 的基线拉高约 4 倍，且真实 3D 场景还要加 MB 级模型 / 贴图。
- **真正的大头是美术与工程**：4 名角色 + 4 个敌人 + 1 张棋盘 + 场景道具的建模、贴图、绑定、待机 / 攻击 / 受击动画，按原型级质量估算约 **2–4 周**（不含外包与反复调优）；这还没有算光照、镜头、移动端适配。
- **构建链**：tree-shaking 需要 bundler（esbuild / Vite / Rollup）。不用构建也能跑，但会退到 419 KB gzip，并且 addons 要逐个管路径。引入后建议锁定 `three@0.187.x`，按迁移指南升级，不要跟随 `dev`。

## 5. 为什么「看起来好用」不等于「适合」

1. **Three.js 的官网示例是技术展示，不是产品画面。** 那些好看的光影、材质、模型，来自示例自带的资产和美术；库本身不提供任何美术。
2. **本项目此前的诊断是「不直观、缺角色 / 卡面」，不是「画不出来」。** 现有 SVG / Canvas 已经能画出雾港、灯塔、木桌棋盘；缺的是人物、卡面和动效。换 Three.js 不解决这个问题。
3. **文字进 3D 是逆操作。** 中文词卡、释义、例句、SRS 按钮都需要清晰排版、选中、读屏；WebGL 里做文字要用位图 / SDF / HTML overlay，成本高、效果差。正确做法是 3D 只做背景 / 棋盘，文字仍然用 DOM。
4. **3D 的维护是持续的。** 一次建模不是终点：新章节、新敌人、新皮肤都要继续产出 3D 资产；2D 的 SVG / Canvas 则可以由代码和少量插画维持。
5. **当前项目是「每天来一把」的轻量学习产品。** 首屏、流量、低端机、离线稳定性比「3D 惊艳」更重要；这与 3A 式 3D 场景的取向相反。

## 6. 与替代方案的位置

| 方案 | 定位 | 许可 | 适合本项目的部分 | 主要代价 | 结论 |
| --- | --- | --- | --- | --- | --- |
| 现状：DOM + SVG + Canvas 2D | 原生 Web | — | 文字、表单、词卡、2D 棋盘、动效 | 3D 表现力有限 | **当前最优**，继续用 |
| **Three.js** | 3D 渲染库 | MIT | 3D 战棋、立体场景、镜头 | 3D 资产 + 构建 + 性能 + 无障碍 | **有条件适合**，先做单场景验证 |
| [PixiJS](https://github.com/pixijs/pixijs)（48.7k★） | 2D 渲染器 | MIT | 2D 场景、粒子、卡牌动效 | 只做渲染，玩法仍自己写 | 2D 升级的优先选项 |
| [Babylon.js](https://github.com/BabylonJS/Babylon.js)（26.3k★） | 完整 3D 引擎 | Apache-2.0 | 需要物理、GUI、编辑器、完整 3D 工作流 | 更重、学习曲线更陡 | 若确定做完整 3D 游戏再考虑 |
| [Phaser](https://github.com/phaserjs/phaser)（40.7k★） | 2D 游戏框架 | MIT | 如果重写整套玩法循环 | 等于重写交互 / 测试 | 不推荐 |

> 如果未来客户端按设计文档走 React / Next.js，React 侧可以用 react-three-fiber 接 Three.js；但它只是 React 绑定，3D 资产与性能问题不变。

## 7. 三种落地方式

### A. 保持现状（推荐）

- 保留 DOM + SVG + Canvas 2D。
- 如果觉得「不够像游戏」，按 [画面调研](game-visual-solutions-survey.md) 的 A / B 路线补：图标、角色立绘、卡框、受击 / 伤害数字、粒子、音效；2D 场景层优先 PixiJS。
- 成本：1–3 天到 1–2 周，不动玩法与测试。

### B. Three.js 只做「战棋 / 场景」一层（有条件）

- 架构：DOM 负责文字、卡牌、按钮、结算；一块 Three.js canvas 夹在背景层，负责棋盘、棋子、场景、光照。
- 适用前提：确定要做**可旋转 / 有高低差 / 立体棋子**的 3D 战棋，而不是「2D 棋盘加一点立体感」。
- 范围：先做**一场战斗**（复用现有战棋原型的规则与 UI 状态），不要碰 12 幕剧情和整章内容。
- 估算：工程 3–5 天（相机、拾取、网格、动画、DOM overlay）+ 美术 2–4 周（模型、贴图、动画、光照）；不含移动端调优与测试补齐。
- 风险：模型风格与雾港的暗色文学感不匹配；3D 棋子在小屏幕上反而更难辨认；低端机掉帧。

### C. 全 3D / 换 Three.js 做整个游戏（不建议）

- 等于重写主界面、词卡、SRS、词书、可访问性和 10 个 E2E；收益只在「全 3D 演出」，与文字学习循环不匹配。
- 除非产品方向改成 3D 冒险游戏，否则投入产出比明显低于 A / B。

## 8. 如果做 B：vertical slice 的最小验收

建议直接在现有战棋原型（PR #11，合并后路径 `prototype/tactical/`）上换渲染层，规则、词卡、教学不动。

**范围**

- 一场遭遇：4 名角色 + 4 个敌人 + 1 张棋盘 + 1 组场景道具。
- 相机：正交等距（固定角度）先做，验证后再加旋转 / 缩放。
- 交互：点击棋子 / 格子选中、移动、攻击；文字与按钮仍是 DOM。
- 资源：先用几何占位（胶囊 + 圆柱 + 底座），验证玩法与性能；再换 glTF 模型。

**验收指标**

| 项 | 门槛 |
| --- | --- |
| 首屏 JS（three + addons，gzip） | ≤ 200 KB，模型 / 贴图懒加载 |
| 帧率 | 中低端 Android 稳定 ≥ 30fps；桌面 ≥ 60fps |
| 交互 | 点选 / 移动无明显延迟；触控目标不小于 44px |
| 可访问性 | 键盘可完成同样操作；减少动效生效；canvas 外有文字状态 |
| 回退 | WebGL 不可用 / 低端机降级回 Canvas 2D |
| 对比 | 同一场景、同一视口、同一主题的 Before / After 截图；至少 3–5 人试玩 |

**决策规则**：如果 3D 版在「谁在打谁、下一步做什么」上并不比 Canvas 2D 更清楚，或者低端机掉到 30fps 以下，就停，不进入第二章。

## 9. 何时重新评估

出现以下任意两条以上，再考虑把 Three.js 提上日程：

1. **3D 成为玩法**：高度、视线、掩体、立体棋子、自由镜头会改变战术决策，而不只是装饰。
2. **有 3D 美术资源**：团队 / 外包能持续产出风格统一的模型与动画，或找到可商用的 CC0 套件并接受其风格。
3. **性能有数据**：目标机型实测能稳定跑目标帧率，首屏与流量可接受。
4. **工程能承担**：接受构建链、版本锁定、升级迁移和 3D 测试成本。
5. **多场景复用**：不是只为一个镜头做 3D，而是后续章节都能复用这套资产与管线。

如果只是想「让画面更像游戏」，优先做 A / B 的 2D 美术与动效，而不是换 3D 渲染器。

## 10. 方法与限制

- GitHub 数据（stars / forks / contributors / issues / 提交 / 版本）与 npm 下载量均为 **2026-11-10** 时点，之后会变化。
- 包体为本地 esbuild 实测，只代表「代码」；真实 3D 场景还要加模型、贴图、音频，通常是 MB 级。
- **未做真机性能 benchmark**，未做 3–5 人试玩，未实际搭建 3D vertical slice；美术 2–4 周、工程 3–5 天都是原型级估算，不是排期承诺。
- 未评估付费 3D 素材、AI 生成模型与外包；这三条可能改变 3D 的成本结构，但不在本次 GitHub 调研范围。
- 本文不替代设计决策：如果产品方向明确要 3D 战棋，应按第 8 节先验证，而不是直接全量迁移。
